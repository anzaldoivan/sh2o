# SH-2 model harness (GPL)

License: GPL-2.0-or-later; see [LICENSE](LICENSE). The files in this folder have a license that is not the license of the sh2o library (MIT). sh2o never links this harness into `libsh2o` and never installs it.

`fixed_harness.c`, `k_harness.c`, `gte_harness.c`, `psyq_harness.c`, `list_harness.c`, `zam_harness.c`, `dpct32_harness.c` and `prepared_harness.c` run the SH-2 object code of the fixed, k, gte, psyq, list, zam, dpct32 and prepared families in the SH-2 interpreter of Yabause, without changes. It includes `harness.c` from the SH2ZAM submodule (`external/SH2ZAM/saturn/benchmarks/sh2-model`) without changes. Yabause is GPL. The build gets the Yabause source at one pinned commit when you run the test. The repository does not keep a copy of Yabause.

## Run

```sh
make sh2-model
```

The target does these steps:

1. In the Yaul image, with no network: it finds the families. A family `<f>` has `benchmarks/<f>-model/bridge.c`, `<f>_harness.c` in this folder and `tests/<f>_oracle.h`; a missing file stops the build. A family with no oracle file (psyq, dpct32, prepared) is accepted only when its harness source has the `--plant-known` switch. For each family it builds two ELFs, `build/sh2-model/native/<f>-model.elf` and `build/sh2-model/portable/<f>-model.elf`. Each ELF has the family's bridge and the library; the fixed family uses [`../fixed-model/bridge.c`](../fixed-model/README.md), the k family [`../k-model/bridge.c`](../k-model/README.md), the gte family [`../gte-model/bridge.c`](../gte-model/README.md), the psyq family [`../psyq-model/bridge.c`](../psyq-model/README.md), the list family [`../list-model/bridge.c`](../list-model/README.md), the dpct32 family [`../dpct32-model/bridge.c`](../dpct32-model/README.md), the prepared family [`../prepared-model/bridge.c`](../prepared-model/README.md). A family with `tests/suite/sh2o_<f>_test_suite.c` also has its suite in the ELF.
2. On the host: it gets the pinned Yabause source into `.cache/yabause` (the make default of `YABAUSE_SOURCE`; set it to use a different folder). It stops if the source is at a different commit or has changes. Then it builds each family's harness with the host compiler, into `build/sh2-model/<f>_harness`. Steps 3 to 5 run for each family; a failure in one family does not stop the others, but the target fails.
3. The harness checks the bridge table of each ELF. Then it runs each vector of `tests/<f>_oracle.h` (783 for fixed, 518 for k on each kernel path, 195 for gte, 88 for list; for dpct32, the 13 DPCT vectors of `tests/gte_oracle.h` through each of its two functions; for prepared, the 71 MVMVA vectors of `tests/gte_oracle.h` at four SR.S settings) on each ELF and compares the result bytes with the oracle. At the first difference, it prints the difference and stops.
4. When the two ELFs agree with the oracle, the harness prints the minimum, maximum and mean cycles and instructions for each ELF and each function. It also prints the pins (SH2ZAM, Yabause, Yaul image) and the SHA-256 of each ELF.
   For k, the harness then runs the suite's digests over all 113,471 vectors and compares them with the pins of `tests/suite/sh2o_k_test.h`. In the native ELF, each of the six test mutants must give a digest that is not its pin. A digest runs as a chain of calls of a resumable `_part` function, 8,192 vectors in each call, because SH2ZAM's harness stops a call at 100,000,000 instructions; the harness prints the most instructions of one call. Then it runs the entry, `_w` and `_w2` wrappers of the four MAC.W functions with `SR.S` = 1: an entry or `_w2` difference fails the run; the `_w` kernels assume `SR.S` = 0, so their counts are printed only. It also prints the mean MODELLED cycles of `_w` and `_w2` at `SR.S` = 0 and their difference.
   For psyq (no oracle file), the harness computes the suite digest over the 1,216 cases in the ELF, 256 cases in each call, with the 6 `ratan2` known answers, and compares it with the pin of `tests/suite/sh2o_psyq_test.h`. Then it runs each case again: the ELF draws the case, the harness calls the body directly, and the ELF adds the case to the hash. This chain must also give the pin. The figures are the cycles of one body call for each body. A wrong digest or known answer stops the run. In each ELF, it runs each case again with `SR.S` = 1; a hash that differs fails the run.
   For gte, the harness calls `sh2o_gte_write`, `sh2o_gte_command` and `sh2o_gte_read` directly for each vector, and the figures are the cycles of one `sh2o_gte_command` call for each opcode. Then it computes the suite digest over the 3,840 cases in the ELF, 256 cases in each call, with the 14 known answers, and compares it with the pin of `tests/suite/sh2o_gte_test.h`. A wrong digest or known answer stops the run. In each ELF, it runs each case and each `cmd` vector again with `SR.S` = 1; a result that differs fails the run.
   For list, the harness calls `sh2o_gte_write`, `sh2o_gte_mvmva_list` and `sh2o_gte_read` directly for each vector. It writes the fifth argument of the list (`out`) on the stack, at R15 of the call. Then, for each vector, it runs each item from the same image through one `sh2o_gte_mvmva` call; these singles must give the result of the vector. Then it computes the suite counts in the ELF in one `sh2o_list_test_counts` call and compares them with the pins of `tests/suite/sh2o_list_test.h`. Wrong counts stop the run. The figures are the cycles of one list item (one list call divided by its n) and of one `sh2o_gte_mvmva` call. In each ELF, it runs each vector again with `SR.S` = 1; a result that differs fails the run.
   For zam (no oracle file; only with `SH2O_ZAM=ON`), the harness computes the zam suite in the ELF over its 118,347 items, 512 items in each call, and compares rc, the counts, the digest and the delegate's counters with the pins of `tests/suite/sh2o_zam_test.h`. Then it runs the zam-3, zam-4 and zam-5 trials in the ELF and compares their counts with the pins. Wrong pins stop the run. In the native ELF, it runs each item again with `SR.S` = 1 and prints how many end states differ, core and delegated apart; a core difference fails the run. Then, for each delegated case of set (A), it runs the command with the delegate and with the GTE core's own kernel; the 64 words of `sh2o_gte_read` must be equal; in the native ELF, the delegate's call runs again with `SR.S` = 1 and must give the same result and words. Then it runs the trials' case draws as a chain in the ELF and, on each case the delegate accepts, the delegate entry and the core entry of TransposeMatrix, SetFogNearFar and the MVMVA list on the same input; the outputs must be equal, and the chain's counts must be the trials' pins. In the native ELF, each accepted delegate call runs again with `SR.S` = 1; the harness prints the differing calls per op, and a difference fails the run. The figures are the cycles of one `sh2o_gte_command` call for MVMVA, RTPS and RTPT, and of one call of each trial entry (the list also per item), delegate and core. See [`../zam-model/README.md`](../zam-model/README.md).
5. The target runs the harness again with `--plant 0`, which changes one bit of one expected result. The harness must fail. Its output is in `build/sh2-model/<f>-plant.out` and `<f>-plant.err`. A family with no oracle file runs with `--plant-known 1` instead: the harness changes bit 0 of the expected value of known answer 1 in the RAM of the ELF and must stop with exit code 1 and "known answer". Its output is in `<f>-plant-known.out` and `<f>-plant-known.err`. A harness with the `--plant-digest` switch (gte, psyq, zam) also runs with it: the harness compares the digest with the pin XOR 1 and must stop with exit code 1. Its output is in `<f>-plant-digest.out` and `<f>-plant-digest.err`. A harness with the `--plant-count` switch (list) also runs with it: the harness compares the suite counts with the pins where the item count is XOR 1 and must stop with exit code 1. Its output is in `<f>-plant-count.out` and `<f>-plant-count.err`.

## The option SH2O_ZAM

```sh
make sh2-model SH2O_ZAM=ON
```

`SH2O_ZAM` is `OFF` by default. With `OFF`, the target does the steps above, and a family whose bridge has the line `sh2_model-option: SH2O_ZAM` (zam) does not run. With `ON`, the target uses the folder `build/sh2-model-zam`, and every family runs (fixed, k, gte, psyq, list, zam, dpct32 and prepared). The Yabause source stays in `build/sh2-model/yabause`. For each build mode, the elf step first builds the SH2ZAM sources `external/SH2ZAM/saturn/src/*.c`, without changes, into `build/sh2-model-zam/<mode>/libsh2zam.a`, with `-DSH2Z_REQUIRE_SH2=1` (native) or `-DSH2Z_FORCE_PORTABLE=1` (portable). The library, the bridges and the suites get the same flags as with `OFF`, plus `-DSH2O_ZAM=1`, the SH2ZAM include folder and the same SH2Z define. The link adds `--gc-sections` and the archive. Each global symbol of the bridge is a root of `--gc-sections`, and the ELF must have each of these symbols. The other families must give the same oracle results, digests and counts as with `OFF`.

## MODELLED figures

The cycle figures are MODELLED. The model has flat RAM. It has no caches, no wait states and no bus contention. They are not Saturn timings.
